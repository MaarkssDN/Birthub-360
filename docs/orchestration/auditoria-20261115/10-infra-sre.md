## 2. PROPOSTAS DE MELHORIA

1. **Consolidar um único runbook por ambiente real.** Reescrever `RUNBOOK.md` removendo as seções OCI/Render/k8s mortas e criando runbook do EC2 real (comandos `docker ps/logs/exec` já usados no DEPLOY_EC2.md) — hoje o documento mais consultado em incidente aponta para arquivos inexistentes.
2. **Transformar deploy EC2 em release imutável.** Construir imagem `birthhub-app:<sha>` no servidor (ou registry), `docker run` com tag imutável, healthcheck `/health/ready` como gate, e rollback = `docker tag`/`run` da tag anterior — substituindo `docker cp dist` + `docker restart` (ver P1-2).
3. **Backup de produção**: hoje **não existe backup automático** (`PRODUCTION_ARCHITECTURE.md` §4). Propor `pg_dump` agendado + snapshot EBS + cópia do volume MinIO para S3, com restore testado (há `scripts/deploy/rollback-drill.sh` — mas ver P1-1, ele é fake).
4. **Observabilidade de produção EC2**: subir o profile `observability` (Prometheus) no compose de produção ou instalar Prometheus+node-exporter na EC2; sem isso, os alertas do `alert.rules.yml` não têm onde rodar em prod.
5. **Alertmanager com receptor real**: `alertmanager.yml` existe e está wired (`docker-compose.opensource.yml:140-149`) mas depende de `SLACK_WEBHOOK_URL`; definir canal e documentar no runbook. Corrigir comentário obsoleto em `alert.rules.yml:3-8` que afirma "não há Alertmanager configurado".
6. **SLO/SLI versionado**: definir SLO de disponibilidade/latência (ex.: 99,5% em `/health/ready`, p95 < 2s) e error budget — hoje só há limiares de alerta, sem objetivo.
7. **Imutabilidade de tags**: `values.yaml:19` usa `tag: 'latest'` e os manifests OCI usam `:latest` em ~15 imagens — pinar por digest/tag semver para reprodutibilidade e rollback.
8. **Dashboards Grafana versionados** em `infrastructure/observability/dashboards/` (lacuna já reconhecida no RUNBOOK §8).
9. **Secrets management em k8s**: quando o caminho Helm for ativado, usar External Secrets/Sealed Secrets ou secret manager em vez de `secret.yaml` gerado de `values.yaml` (`templates/secret.yaml` renderiza `b64enc` de valores versionados — hoje comentados, mas o mecanismo convida a commitar segredo).
10. **Eliminar duplicatas de compose**: `temporal`/`temporal-ui`/`qdrant`/`postgres` definidos em overlays sobrepostos (`docker-compose.opensource.yml` × `docker-compose.services.yml` × `docker-compose.qdrant.yml`) geram merge conflitante; consolidar em um único arquivo de serviços opcionais.

## 3. ERROS, FALHAS E DÍVIDAS

### P0 — Crítico

- **P0-1. Docker daemon remoto sem autenticação exposto na LAN.** `192.168.0.116:2375` aceita Engine API sem TLS/auth — qualquer host da LAN `192.168.0.0/24` cria containers privilegiados e lê todos os volumes (Postgres, Redis, MinIO) com todas as credenciais. Mitigação versionada (`infrastructure/security/apply-docker-2375-allowlist.ps1`) mas **pendente de execução no host** (`DOCKER-REMOTE-DAEMON.md:1-4`). Agravante documentado: portas 5434/6379/7700/9000/4000/11434/5435/6380 também escutam em `0.0.0.0` (`DOCKER-REMOTE-DAEMON.md` §Passo 3). Risco LGPD/segurança P0 até aplicação.
- **P0-2. Sem backup de produção.** `PRODUCTION_ARCHITECTURE.md` §4: "não existe backup automático de produção"; workflow de backup removido (PR #181). Postgres, MinIO e Qdrant em disco único na EC2 sem cópia — perda do host = perda total de dados de clientes (LGPD: obrigação de disponibilidade/recuperação).
- **P0-3. Scripts de verificação de deploy são falsos.** `scripts/deploy/production-smoke-tests.sh` não executa nenhum curl — apenas faz `echo` de "200 OK" e `exit 0` (linhas 10-23). `scripts/deploy/rollback-drill.sh` idem: imprime "Reversão executada com sucesso" sem reverter nada (linhas 3-15). Evidência fabricada de QA/rollback — viola P4 do AGENTS.md e dá falsa sensação de rollback testado.

### P1 — Alto

- **P1-1. Deploy de produção muta container em execução, sem release imutável nem rollback automático.** `deploy-aws.ps1:66-70` faz `docker cp dist` dentro do container vivo + `docker restart`; `deploy-ec2.sh:24-25` copia `node_modules` via SCP (frágil, mistura binários) e `deploy-ec2.ps1` idem com `dist-new`. Backup `cp -r dist dist.backup` é **sobrescrito a cada deploy** (`deploy-aws.ps1:57`) — não é timestamped nem restaurável automaticamente. Healthcheck pós-deploy existe (`deploy-aws.ps1:78-101`) mas **falha não dispara rollback** — apenas `exit 1`.
- **P1-2. Runbook de produção aponta para arquivos deletados.** `RUNBOOK.md` seções "0-OCI" (linhas 306-347), "Rollback via Oracle Cloud" (514+) e `PRODUCTION_ARCHITECTURE.md` §2 citam `docker-compose.oci.yml`, `scripts/deploy-oci.sh`, `docs/deploy/oracle-cloud.md` — inexistentes desde commit `783f85821`. Em incidente real, o operador seguirá instruções mortas.
- **P1-3. Produção EC2 provavelmente sem observabilidade centralizada.** `PRODUCTION_ARCHITECTURE.md` §2 lista Prometheus/Grafana/Loki/Tempo via `docker-compose.oci.yml` — arquivo deletado; não há evidência no repo de stack de observabilidade no compose de produção EC2. Todos os alertas de `alert.rules.yml` são inertes em prod se nada os scrapeia. `DEPLOY_EC2.md` não menciona Prometheus/Grafana na stack de produção (lista só app/postgres/redis/meilisearch/minio/litellm/ollama/qdrant).
- **P1-4. `StrictHostKeyChecking=no` em todos os SSH de deploy.** `deploy-aws.ps1:54,57,61,62,66,70,83,104,107` e scripts afins desabilitam verificação de host key — MITM trivial na primeira conexão; a chave `.pem` e todo o `dist`/deploy podem ser interceptados.
- **P1-5. Merge conflitante entre overlays de compose.** `docker-compose.services.yml:127-158` define `temporal`/`temporal-ui` e `docker-compose.opensource.yml:175-226` também os define com imagens, portas e env diferentes (`auto-setup:1.24.2`+porta UI `8233` vs `auto-setup:latest`+UI `8088`; env `DB`/`POSTGRES_PWD` vs `DB_PORT`/`POSTGRES_USER`). O próprio header do services.yml (linha 4) manda combinar os dois arquivos — o merge produzirá definições ambíguas/duplicadas de portas de container. `qdrant` existe em `services.yml:286` e `docker-compose.qdrant.yml:6` com mesmo `container_name`/volume.
- **P1-6. ArgoCD Applications apontam `values.yaml` único para homolog e produção com sync automático total.** `argocd/application-production.yaml` e `application-homolog.yaml` usam o mesmo `path: charts/birthhub-360` + `values.yaml` (sem values file por ambiente), `targetRevision: main`/`develop`, `automated: prune+selfHeal`. Se ativado: homolog e prod idênticos (mesmo host `birthhub-360.local`, `values.yaml:65`), tag `latest` mutável (`values.yaml:19`), e qualquer push em `main` auto-deploya produção sem gate. Não há `values-homolog.yaml`/`values-production.yaml`.

### P2 — Médio

- **P2-1. Segredos com defaults fracos em plaintext versionados (dev overlays).** `docker-compose.services.yml`: `INFISICAL_ENCRYPTION_KEY` default `0000...` (linha 265), Casdoor `admin/123456` documentado (linha 238), `N8N_ENCRYPTION_KEY`/`SUPERSET_SECRET_KEY`/`PLANE_SECRET_KEY`/`CHATWOOT_SECRET_KEY`/`OPENWEBUI_SECRET` todos com fallback `change-this-*` (linhas 99,169,331,411,70); `docker-compose.yml:12` Redis `requirepass` default `prospector_redis_pass`; `docker-compose.opensource.yml:17-19` Langfuse `NEXTAUTH_SECRET`/`SALT`/`ENCRYPTION_KEY` defaults; Grafana admin `change-this-grafana-password` (linha 164). ## Resumo executivo

O chart Helm e a camada de observabilidade **versionada** estão em excelente estado (probes reais, migração bloqueante, alertas honestos, runbook extenso). Os riscos concentram-se em: **(a)** produção real = EC2 com deploy mutável sem rollback/backup/observabilidade, (b) documentação de runbook apontando para caminho OCI deletado, (c) scripts de smoke/rollback **falsos**, (d) daemon Docker 2375 sem auth pendente de contenção, e (e) defaults de segredo e imagens `:latest` nos overlays de dev que vazam para LAN.
