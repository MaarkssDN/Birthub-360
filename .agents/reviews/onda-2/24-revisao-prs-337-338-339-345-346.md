## PR #337 — `agente/01a-onda2-handoffs` (Agente 01A — auditoria tenancy CRM/CRM360)

**Commits auditados:** `ce0455e9d`, `87b9205d` (branch `agente/01a-onda2-handoffs`).

**Verificações realizadas pelo auditor:**

1. Os 3 fixes de `organizationId` no `where` estão corretos:
   - `LeadUseCases.enqueueBatchEnrichment`: `prisma.company.updateMany({ where: { id: { in: companyIds }, organizationId } })` — `Company.organizationId` existe (schema L195+); `organizationId` é parâmetro da função, nunca de input do cliente.
   - `LeadUseCases.batchUpdateLeads`: `prisma.lead.update({ where: { id: lead.id, organizationId } })` — ids vêm de `findMany` já escopado por `{ id: { in: leadIds }, organizationId, deletedAt: null }`; Prisma 7.10 suporta campos não-únicos em `where` de update (extendedWhereUnique). Falha vira P2025 (fail-closed), nunca update cross-tenant.
   - `PrismaCrm360Repository.recordDocumentView`: update dentro de `requestContext.run({ tenantId: doc.organizationId })` com `where: { id, organizationId: doc.organizationId }` — o lookup prévio usa `bypassRls` somente para `findUnique` por `publicToken` (credencial opaca), padrão documentado e consistente com `BYPASS_RLS_ALLOWED_MODELS`.
2. Alegação "sem vazamento cross-tenant": o modelo de 3 camadas descrito no handoff foi confirmado em código — `authenticateToken` (`src/shared/middlewares/authenticateToken.ts:83`) popula `requestContext.run({ tenantId: user.organizationId })`; `requireTenant` montado nas rotas (`src/bootstrap/routes.ts:98-110`); `SET LOCAL app.current_tenant_id`/`app.bypass_rls` no client estendido (`src/lib/prisma.ts:257`); `injectTenantIntoWriteArgs`/`TENANT_INJECTED_MODELS` (`src/lib/prisma-interceptors.ts:187`, `src/lib/tenant-scoping-registry.ts:42`). Amostragem do auditor nos pontos de escrita do diff: consistente. Não foi feita re-varredura exaustiva dos ~50 pontos — a evidência estrutural + amostragem sustenta a alegação dentro do escopo declarado.
3. Handoff aberto `01a-para-04` (batchUpdateLeads grava rótulo cru no enum `Lead.status`, bypassa gate CYC-007) é legítimo, bem documentado e corretamente endereçado ao dono do domínio (04).

**Conflitos de merge com `origin/main`:** SIM — `git merge-tree` reporta conflito em `.agents/handoffs/onda-paralela-8/00-para-01a-tenancy-audit.md` e `src/features/crm360/infra/PrismaCrm360Repository.ts`. Causa: a main refatorou `PrismaCrm360Repository` — `recordDocumentView` migrou para `src/features/crm360/infra/PrismaCrmDocumentRepository.ts` (L477-497), que **ainda contém o update sem `organizationId` no `where`**. Os 2 fixes de `LeadUseCases.ts` não conflitam e seguem necessários (main ainda tem `where: { id: lead.id }` em L721 e `where: { id: { in: companyIds } }` no updateMany).

**Veredicto: APROVADO-COM-RESSALVAS.** Trabalho correto e evidenciado, mas o merge exige rebase: (a) resolver conflito do handoff doc; (b) re-aplicar o 3º fix no novo arquivo `PrismaCrmDocumentRepository.ts` (o conflito em `PrismaCrm360Repository.ts` deve ser resolvido mantendo a refatoração da main — o fix precisa ser portado, não descartado).
