**Verificações realizadas pelo auditor:**

1. Os 3 fixes de `organizationId` no `where` estão corretos:
   - `LeadUseCases.enqueueBatchEnrichment`: `prisma.company.updateMany({ where: { id: { in: companyIds }, organizationId } })` — `Company.organizationId` existe (schema L195+); `organizationId` é parâmetro da função, nunca de input do cliente.
   - `LeadUseCases.batchUpdateLeads`: `prisma.lead.update({ where: { id: lead.id, organizationId } })` — ids vêm de `findMany` já escopado por `{ id: { in: leadIds }, organizationId, deletedAt: null }`; Prisma 7.10 suporta campos não-únicos em `where` de update (extendedWhereUnique). Falha vira P2025 (fail-closed), nunca update cross-tenant.
   - `PrismaCrm360Repository.recordDocumentView`: update dentro de `requestContext.run({ tenantId: doc.organizationId })` com `where: { id, organizationId: doc.organizationId }` — o lookup prévio usa `bypassRls` somente para `findUnique` por `publicToken` (credencial opaca), padrão documentado e consistente com `BYPASS_RLS_ALLOWED_MODELS`.
2. Alegação "sem vazamento cross-tenant": o modelo de 3 camadas descrito no handoff foi confirmado em código — `authenticateToken` (`src/shared/middlewares/authenticateToken.ts:83`) popula `requestContext.run({ tenantId: user.organizationId })`; `requireTenant` montado nas rotas (`src/bootstrap/routes.ts:98-110`); `SET LOCAL app.current_tenant_id`/`app.bypass_rls` no client estendido (`src/lib/prisma.ts:257`); `injectTenantIntoWriteArgs`/`TENANT_INJECTED_MODELS` (`src/lib/prisma-interceptors.ts:187`, `src/lib/tenant-scoping-registry.ts:42`). Amostragem do auditor nos pontos de escrita do diff: consistente. Não foi feita re-varredura exaustiva dos ~50 pontos — a evidência estrutural + amostragem sustenta a alegação dentro do escopo declarado.
3. Handoff aberto `01a-para-04` (batchUpdateLeads grava rótulo cru no enum `Lead.status`, bypassa gate CYC-007) é legítimo, bem documentado e corretamente endereçado ao dono do domínio (04).

**Conflitos de merge com `origin/main`:** SIM — `git merge-tree` reporta conflito em `.agents/handoffs/onda-paralela-8/00-para-01a-tenancy-audit.md` e `src/features/crm360/infra/PrismaCrm360Repository.ts`. Causa: a main refatorou `PrismaCrm360Repository` — `recordDocumentView` migrou para `src/features/crm360/infra/PrismaCrmDocumentRepository.ts` (L477-497), que **ainda contém o update sem `organizationId` no `where`**. Os 2 fixes de `LeadUseCases.ts` não conflitam e seguem necessários (main ainda tem `where: { id: lead.id }` em L721 e `where: { id: { in: companyIds } }` no updateMany).

**Veredicto: APROVADO-COM-RESSALVAS.** Trabalho correto e evidenciado, mas o merge exige rebase: (a) resolver conflito do handoff doc; (b) re-aplicar o 3º fix no novo arquivo `PrismaCrmDocumentRepository.ts` (o conflito em `PrismaCrm360Repository.ts` deve ser resolvido mantendo a refatoração da main — o fix precisa ser portado, não descartado).

## PR #339 — `agente/12-onda2-handoffs` (Agente 12 — voice-hub models canônicos)

**Commits auditados:** `6a1394c5c`, `c3e37014b`, `968f7c66` (branch `agente/12-onda2-handoffs`).
**Escopo:** 83 arquivos, `src/lib/voice-hub/**`, `src/features/voice-hub/**`, `tsconfig.voice.json`, handoffs.

### Pontos fortes verificados

1. **Remoção do JWT próprio** (`lib/auth-tokens.ts` reduzido a `TokenPayload`; `services/authService.ts` deletado; `routes/auth.routes.ts` só `/auth/me` + `/auth/logout` via Better Auth) — reduz superfície de auth paralela. Validators `registerSchema`/`loginSchema` removidos.
2. **`requestContext`/RLS correto:** `attachAuthIfPresent` popula `requestContext.run({ tenantId, userId, role })` quando a autenticação é estabelecida pela própria middleware (API key ou `getSession` Better Auth); quando `authenticateToken` já rodou, preserva a store upstream (comparação `store.tenantId !== session.organizationId`). O `getSession` roda sob `bypassRls` — mesmo padrão documentado de `authenticateToken` (Session/User têm FORCE RLS).
3. **RBAC fail-closed:** `voiceRoleForCanonicalRole` mapeia `ADMIN→admin`, `GESTOR→supervisor`, todo o resto (incl. null/desconhecido)→`user`; `getPermissionsForRoleName` retorna `[]` para voice-role desconhecido e faz union com capability grants só quando `userId` é informado; falha na query de capabilities degrada para defaults (nunca amplia).
4. **Isolamento por tenant nos services:** `userService.deleteUser`/`anonymizeUserData`/`updateUserProfile` verificam `target.organizationId !== organizationId → 404` antes de agir; `deleteUser` mantém trava de "único ADMIN"; `sessionService` valida ownership via `findSessionForUser(org+user)` antes de update/delete; `notificationRepository`/`notificationService` escopam tudo por `{ organizationId, userId }` (org nunca de input do cliente); `auditLogRepository.createAuditLog` rejeita sem `organizationId` (AuditLog.tenantId NOT NULL) e `listAuditLogsForTenant` resolve `actorEmail` somente dentro do mesmo tenant; `apiKeyService.authenticateApiKey` exige `user.organizationId === apiKey.organizationId`.
5. **Adaptação a models canônicos correta:** `sessionRepository→agentSession` (não `Session` do Better Auth — comentário explícito), `tenantRepository→organization`, `userRepository→User/Account credential Argon2id/UserJobRole/JobRole`, `roleRepository→JobRole/RoleCapabilityGrant/CapabilityDefinition`, `notificationRepository→body/readAt`, `auditLog→tenantId/actorId/details texto`, `webhookEndpoint→organizationWebhookEndpoint`, `birthhub360CallResult→birthub360CallResult` (grafia confirmada no schema L5414). Nomes de função `*Tenant*` mantidos por compatibilidade — semanticamente corretos.
6. **`updateUser` usa `runInTransaction(fn, { organizationId })`** — não `prisma.$transaction` cru (correto: o plugin `no-prisma-tx-escape` e a RLS exigem tenant no contexto). `anonymizeUser` usa `$transaction` cru com biome-ignore justificado (anonimização LGPD atômica) — usuário+contas+sessões+jobRoles na mesma tx.
7. **`express.d.ts` `organizationId: string` non-optional:** seguro porque (a) `src/lib/voice-hub` está excluído do `tsconfig.json` principal — a augmentation global só vale em `tsconfig.voice.json`; (b) todo router do módulo passa por `requireTenant`; (c) congelado por `tenant-isolation.test.ts` (36 testes).
8. **Gate de reabertura preservado:** `src/bootstrap/routes.ts` NÃO foi tocado — `/api/voice-hub`, `/api/outbound`, `/api/dialer-3cx` seguem em `unavailableLegacyModule` (503). O próprio handoff do 12 mantém NO-GO até: decisão de deps (`twilio`/`d3`/`openid-client` ausentes do package.json — decisão do 00), teste de integração RLS real, e parecer do 24.
9. Nenhum `organizationId`/`tenantId` lido de `req.body`/`req.params`/`req.query` nos controllers auditados — sempre de `req.organizationId`/`req.voiceHubUser` populados pela sessão.

### Achados

- **ACH-1 (normal, contrato):** `attachAuthIfPresent` sobrescreve `req.user` canônico com o `TokenPayload` voice-role, contradizendo o próprio comentário. Latente (gate 503), fail-closed na maioria dos cenários, mas é divergência de contrato — **handoff `.agents/handoffs/onda-2/24-para-12-voicehub-attachauth-sobrescreve-req-user.md`** criado.
- **ACH-2 (info, já registrado pelo 12):** `retentionScheduler`/`slaScheduler` corrigidos para BullMQ v6 mas não wired no boot/worker; deps npm ausentes impedem `tsc -p tsconfig.voice.json` de zerar; teste de integração Postgres/RLS real ainda não executado (mocks não provam policy). Tudo já consta no checklist aberto do handoff `12-para-00-voicehub-tenancy-auditoria.md`.
- **ACH-3 (info):** `conflitos de merge` apenas em 2 handoffs docs (`12-para-01-...`, `00-para-12-hotspots...`) — trivial.

### Limitações desta revisão

- Os 600 testes e o `tsc -p tsconfig.voice.json` (313→14 erros, restantes = deps ausentes) **não foram re-executados** pelo auditor; a evidência é a declarada pelo 12 + verificação estática do diff. Como o módulo está atrás do `legacyModuleGate` (503), o risco de merge é baixo.
- A prova definitiva de isolamento depende do teste de integração RLS real — pendente e corretamente mantida como condição de GO.

**Veredicto: APROVADO-COM-RESSALVAS.** A adaptação é tecnicamente sólida, fail-closed e preserva isolamento; o merge pode prosseguir após rebase trivial dos 2 handoffs e, idealmente, correção do ACH-1 (não bloqueante para merge dado o gate fechado, mas recomendada antes de qualquer reabertura do módulo). **Esta aprovação NÃO autoriza reabrir o `legacyModuleGate`** — o GO continua condicionado a: decisão de deps (00), teste de integração RLS real, e os handoffs abertos a 05 (`/api/outbound` sem auth) e 17 (`/api/dialer-3cx` sem auth/tenant).
